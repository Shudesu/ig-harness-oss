# 第4章 キャンペーン設計 🔒

> 【tier: 🔒有料】Engagement Gates を「獲得装置」として設計する。Standard Access の制限を踏まえた現実的なキャンペーン設計図を提示する。

## 章の目的
- フォロワー獲得・リード獲得を目的としたキャンペーンを、ゼロから設計できる

- 投稿クリエイティブ／キャプション／ゲート文言／DM 文面 の整合性を取れる

## 想定読者
- 第3章まで読了し、自分のアカウントで実フロー設計に入る運用者
- 既存の ManyChat キャンペーンを移植したい人

## 4.1 設計の原則 — 「IG の DM に依存しすぎない」「リスト化は LINE 側」

ManyChat 文化で IG 自動化を覚えた人は、ほぼ全員が同じ罠に落ちる。「IG の DM フローを完璧に組めば、IG だけで収益化まで完結する」という誤解だ。これは半分正しく、半分間違っている。

正しい部分は、IG の DM が **1:1 配信** であることだ。コメントは公開広場、フィードはアルゴリズム任せ、ストーリーズは 24 時間で消える。そんな中で DM だけは、相手の受信箱に直接届けられる唯一のチャネルになる。だからこそ ManyChat も IG Harness も、DM を主戦場に据える。

間違っている部分は、「IG の DM は中長期的な nurture チャネルとして弱い」という事実を無視している点だ。Meta は IG ビジネスアカウントから能動的に送れる DM に厳しい制約を課している。本実装の通常DMはユーザーの最終応答から **24時間以内** に限定する。自動配信の期限をタグで延長することはしない。HUMAN_AGENT等の人手サポート向け例外や他製品の機能を、自動ステップ配信へ流用しない。

つまり IG 単体の構造は、こうなる。

| フェーズ | IG で出来ること | IG の限界 |
|---|---|---|
| 認知 | 投稿・リール・ストーリーズ | アルゴリズム依存、ストック性が低い |
| 接点取得 | DM 起点フック（4.4 で詳述） | 24h ウィンドウで DM が枯れる |
| 関係深化 | 応答後のDM・ステップ配信 | 相手の新しい応答がなければ24時間で送信を終了 |
| 売上化 | LP 誘導 | IG → ブラウザ離脱率が高い |

この表を見ればわかる通り、IG は **「認知から接点取得までは強いが、関係深化と売上化には別チャネルが要る」** メディアだ。ここを見誤ると、頑張って組んだ DM フローが「24 時間で枯れるリスト」を再生産し続ける装置になる。

本章で扱うキャンペーンは、この前提の上に立つ。

- **設計原則 1**: IG の DM は「初回接点を取る装置」と割り切る。中長期 nurture は LINE に逃がす（第 5 章）。
- **設計原則 2**: コメント返信に過度に依存しない。対象アカウントの権限条件と、コメント欄の運用負荷を確認する（4.2）。
- **設計原則 3**: フォロワー獲得とリスト獲得は別目的として扱う。同じ DM フローで両方を狙うと文面がぼやける（4.3）。

ManyChat 移行組がよく持つ「IG だけで完結させる」という前提は、ここで一旦捨ててほしい。捨てた上で IG Harness の設計を見ると、なぜ engagement gate と LINE cross-link がセットで提供されているかが腹落ちする。

## 4.2 Access Level・permission・送信ウィンドウを確認する

過去のv0.5系の実測を全アプリへ一般化しない。Meta公式では、Standard/Advancedの境界は対象アカウントの所有・管理とApp Dashboardへの登録等で説明される。`POST /{ig-comment-id}/replies` がStandardで必ず失敗する、という断定は置かない。対象やpermissionが違えば同じエラーになる場合があり、個別に確認する。

ゲートの公開コメントはトップレベルのmention、コメントルールはスレッド返信。前者を後者の権限回避策とは扱わない。どちらも必要な権限・Access Levelを満たすことが前提となる。

コメントからの最初のDMはprivate replyで1通。その後のカード・ボタン・画像・シナリオは相手の返信後に送り、本実装では最終inboundから24時間内に限定する。コメントだけで通常DM枠が開いたとはみなさない。standby通知では応答しない。

初回文面と返信後の内容は分けて確認する。既存の特典内容は保持し、画像やテンプレートは返信後まで待つ。公開コメントの失敗・API待機・期限外は管理画面の「配信状況」に表示する。[検証した一次資料と実装範囲](../operations/meta-api-audit-20261026.md)も参照。

## 4.3 エンゲージメントゲートとフォロワー獲得設計

第 3 章で扱った engagement gate は、機能としては「フォロー有無を判定して DM を出し分ける」装置だが、キャンペーン設計の文脈では **「ガラ受け（フォローしないリード）を最初から弾く装置」** として使う。

ここを取り違えると、せっかくの DM フローが「特典だけ持って消える人」を量産することになる。

### ガラ受け問題

ManyChat 時代に多くの運用者が抱えた不満が、いわゆる「特典 DM だけ受け取って、フォローもされず、後続のステップ配信にも反応しない」現象だ。これは UX の問題ではなく、構造の問題で起こる。

- ユーザーが投稿のコメント欄でキーワードを打つ → DM で特典 URL が届く
- ユーザーは特典だけ取得 → そのままフォロー解除 or ミュート
- 運用者から見ると DM 配信ログは増えているが、フォロワー数は伸びない

IG Harness の engagement gate はこの構造を逆転させる。**特典の前に「フォロー判定」を必ず挟む** ことで、フォローしていない人には特典 DM が届かない設計にできる。

### 配信フローの基本形

```
[コメント受信 → 初回private reply 1通 → 相手から返信]
 または [キーワード DM 受信]
        ↓
[24時間枠・応答担当・ゲートの有効状態を確認]
        ↓
[CTA DM を送る:「特典準備できました、下のボタンを押してね」]
        ↓
[ユーザーがボタン押下 → postback webhook]
        ↓
[is_user_follow_business を Graph API でリアルタイム判定]
        ↓
   ┌────────────┴────────────┐
[フォロー済み]              [未フォロー]
   ↓                           ↓
reward DM 配信              リマインド DM
（特典 URL / LINE 誘導）     「フォローしてね」
                              ↓
                          ループ（ユーザーが再度ボタンを押すまで保留）
```

重要な点は 2 つ。

1. **フォロー判定は「ボタン押下時」にやる**。投稿コメント時点ではフォローしているかどうかを聞いても自己申告にしかならない。`is_user_follow_business` は Meta の User Profile API でリアルタイム取得できる項目で、ここで判定すれば嘘をつかれない。
2. **未フォロー時のループは「無限」で良い**。リマインド DM を踏むたびにフォロー判定を再実行するため、ユーザーがフォローした瞬間に reward DM が届く。途中で離脱されても、別企画で再度フックしたときに同じ仕組みが効く。

### フォロワー獲得 KPI の置き方

このゲートを使うキャンペーンでは、KPI を次のように分解する。

| 指標 | 取り方 | 改善対象 |
|---|---|---|
| triggered | コメント or キーワードを踏んだ人数 | 投稿側のフック設計（キャプション / CTA） |
| cta_sent | 初回案内を送れた人数（コメント起点では返信待ちを含む） | private reply後に応答したか、通常DM枠内か |
| pending_follow | ボタンを押したが未フォローだった人数 | リマインド DM の文面 |
| delivered | reward DM まで到達した人数（= ガラ受け除外後） | フォローの心理的ハードル |
| follow_rate | delivered / cta_sent | キャンペーン全体の歩留まり |

ManyChat 時代によくある「コメント数 → DM 配信数」だけを見る KPI は、この文脈では **無意味** に近い。配信数を増やすこと自体は簡単で、本当に欲しいのは「フォローしてくれた人へのリーチ」だからだ。

### 投稿クリエイティブとの整合

このゲートを設計したら、投稿側のクリエイティブとキャプションも整合させる。

- 投稿のキャプション: コメントすべきキーワードを 1 つに絞る（複数キーワード OR 設計はバグの温床）
- 投稿の CTA: 「コメントで『○○』とだけ書いてね」と明示する
- ストーリーズの追い: 同じキーワードを Stories でも使えるように DM フックも併設（4.4）
- ハイライトに「特典の受け取り方」を残す: 過去投稿からの動線も拾う

ここを揃えないと、ゲートだけ立派で入口が狭いキャンペーンになる。

## 4.4 DM 起点シナリオの組み方 — Stories 返信／キーワード DM／保存通知

以下の4種類の入口を設計候補にする。受信可否は対象アカウントのpermission、Appのモード、Webhook購読、応答担当の設定を確認する。コメントだけでは通常DMの送信枠は開かない。

### フック 1: コメント起点（基本）

最もよく使われるが、依存しすぎてはいけないフック。投稿・リールのコメント欄でキーワードを踏ませて DM に逃がす。

設計のコツ:

- キーワードは「短く、特殊文字を含まない、誤入力しにくい」もの。ひらがな 2〜4 文字（例: `じゅしん`、`ほしい`）が無難
- 大文字小文字・全角半角の揺らぎを正規化する処理を IG Harness 側のシナリオに入れる（管理画面のシナリオ設定で「キーワード一致条件」を `contains` ではなく `normalized_match` に近い形で組む）
- 1 投稿に 1 キーワードを基本ルールに。複数オファーを 1 投稿に詰め込まない

### フック 2: ストーリーズ返信

ストーリーズへのDM返信はmessages Webhookで受信する。必要なpermission・購読・Access Levelを満たすことが前提になる。コメント導線との反応率は自分のアカウントで比較する。

設計のコツ:

- ストーリーズに「興味あったら『はい』と返信してね」と入れる（質問スタンプではなく、テキスト返信を促す）
- 質問スタンプは IG の純正機能で集計される一方、それ単体では IG Harness の DM フローには流れない（ストーリーズスタンプは webhook イベントとして別建て、現時点では信頼度が低い）
- リプライ受信時のシナリオは、コメント起点と同じ engagement gate に流せる

### フック 3: キーワード DM（直接 DM）

ユーザーが直接 DM で特定キーワード（例: `特典`、`プレゼント`）を送ってきた場合に発火するフック。投稿やストーリーズで「DM で『特典』と送ってね」と促す形で使う。

設計のコツ:

- DM の最初の 1 通は **必ず 24h ウィンドウを開く** 効果がある。フォロワー獲得というより「DM ウィンドウを能動的に開けさせる」ためのフックとして使う
- LP に「DM で○○と送ってね」リンクを置く場合は、`https://ig.me/m/{username}?text={キーワード}` 形式の deep link を使うと、IG アプリで DM 画面が開いた状態でテキストが入る
- 公式ハッシュタグ `#特典DM` のような俗語に頼らない。キーワードはアカウントごとに独自設定する

### フック 4: メンション

ストーリーDMのメンションは、messages Webhookのstory_mention添付として処理する。投稿本文のメンションやlegacy mentions通知を、通常DMの送信許可とはみなさない。標準購読は第2章の一覧に合わせる。

設計のコツ:

- 自動DMは、実際のinboundと24時間枠・応答担当を確認できる場合にだけ送る
- ただしメンションは UGC 設計が前提で、自然発生数が少ないアカウントでは安定しない。**メイン導線にはせず、補助的な reach 拡張として位置付ける**

### フック 4.5（参考）: 保存通知は使えない

ManyChat の一部チュートリアルで「保存（Save）したユーザーに DM」みたいな記述を見るが、**Meta の Webhook フィールドには「保存通知」が存在しない**（2026 年 4 月時点）。`saved` のようなフィールドは webhook 仕様にないので、これに依存した設計は組めない。代替として「いいねした投稿の保存数」を投稿インサイトで見ることはできるが、これは個別ユーザーに紐付かない統計値だ。

「保存数を伸ばす」設計と「保存したユーザーに DM する」設計は別物なので、後者は捨てる。

### シナリオの組み方（IG Harness 管理画面）

複数フックを 1 つの engagement gate に集約する設計が、運用負荷を最小化する。

```
[engagement gate: ig_campaign_2026_05_lead_magnet]
  ├─ trigger: comment_keyword "じゅしん" on media #12345
  ├─ trigger: dm_keyword "特典" 全媒体共通
  ├─ trigger: story_reply contains "ほしい"
  └─ trigger: mention received in story
              ↓
        [全 trigger 共通の CTA DM]
              ↓
        [follow check ボタン]
              ↓
        [reward DM (LINE 誘導付き)]
```

この形にすると、KPI の `triggered` を fork ごとに見られるので、どのフックが最も効いているかが集計できる。新しい投稿で `comment_keyword` を増やすたびに、同じ gate に紐付ける運用が回しやすい。

## 4.5 LINE 誘導への接続 — IG 完結を諦める判断基準と次章への接続

ここまでの設計を回しても、IG 単体での収益化には構造的な天井がある。これは IG Harness の設計問題ではなく、Meta の DM API 仕様による天井だ。

### IG 完結を諦める判断基準

次のいずれかに該当したら、IG 単体で完結させようとせず、LINE 側に逃がす設計に切り替える。

1. **LTV が ¥10,000 を超える商材を扱っている**: 24h ウィンドウで成立する単発購入なら IG 完結も可能だが、継続課金・教育コンテンツ・コミュニティ販売は nurture が必要なので IG だけでは無理
2. **月の DM 配信数が 1,000 を超え始めた**: IG の DM 配信は API レート制限と「タグ付き / ウィンドウ外」の制約で、ブロードキャストに使うには弱い。1,000/月を超えたあたりから「コストの高い配信」を強いられる
3. **複数キャンペーンを並走させたい**: IG では 1 つの DM スレッドで複数の文脈を捌くことになり、ユーザー側でも運営側でも管理が破綻する。LINE のステップ配信＋ tag 設計の方が圧倒的に楽
4. **同じユーザーに 1 週間後に再接触したい**: IG の DM ウィンドウは 24h で閉じる。1 週間後の配信は事実上不可能（タグ付きメッセージはユースケース限定）

これらに 1 つでも該当するなら、IG 側のキャンペーンを「LINE への流入装置」として再定義した方が、ROI が劇的に変わる。

### IG → LINE 誘導の必然性

IG Harness と LINE Harness が姉妹 OSS として作られている理由は、まさにこのためだ。IG で集めたリードを LINE 公式アカウント側に流し込み、LINE 側でステップ配信・タグ管理・ブロードキャスト・LIFF フォーム回答を行う。

このとき重要な技術的要素は次の通り。

- IG の reward DM 内のリンクを LINE Harness の **tracked link** にする
- tracked link に `?ig=<IGSID>` パラメータを載せる
- ユーザーが LINE 友だち追加すると、LINE Harness 側で `friends.ig_igsid` が記録される
- IG Harness 側にも webhook で通知が飛び、`followers.line_friend_uuid` が記録される
- これにより **同一ユーザーの IG と LINE の ID が双方向リンク** される

この仕組みのおかげで、「IG フォロワー × LINE 友だち」の統合台帳ができる。X の broadcast 配信では実現できない、IG 特有の 1:1 配信を活かした強みだ。

具体的なフロー設計と中間ページの作り方、LIFF URL パラメータの扱い、OAuth 直リンクが NG な理由（IG アプリ内ブラウザの制約）、push 配信のタイミングは、第 5 章でまとめて扱う。

### 本章のまとめ

本章で押さえてほしい要点を 5 つに絞る。

1. **IG の DM は「初回接点」装置と割り切る**。中長期 nurture は LINE に逃がす
2. **返信方法とAccess Levelを混同しない**。Standard/Advancedの条件は対象アカウントの所有・管理とApp登録等で決まる。ゲートはトップレベルのmention、コメントルールはスレッド返信を使うが、どちらもpermissionや審査を回避する方法ではない。
3. **engagement gate は「ガラ受け除外装置」として使う**。フォロー判定をボタン押下時に Graph API で取り、フォロー前提で reward を出す
4. **DM 起点フックは 4 種（コメント / Stories 返信 / キーワード DM / メンション）を冗長化する**。1 種類に依存しない
5. **他製品との比較には運用負荷も含める**。権限条件、送信できる相手、LINE連携を維持する手間を確認して選ぶ

### 次の章

第 5 章では、本章の最後で触れた **IG → LINE 中間ページ + push 配信フロー** を、LIFF URL パラメータ・UUID 引き渡し・連携バッジ表示・DM 自動生成 UX の観点で深掘りする。第 4 章で「IG 完結を諦める」と決めた人が、実際にどう LINE 側に逃がすかの実装設計が中心になる。

第 6 章では、本章で組んだキャンペーンを複数並走させたときの日次／週次オペレーション、KPI ダッシュボードの読み方、トラブル時の切り分けを扱う。
